# Data Model: Financial Assistant Interface

## Existing persisted entities

The UI reads the existing `TransactionOccurrence`, `TransactionObservation`, and `occurrence_observation` link; it does not change their identity or reconciliation rules. Each occurrence has zero or more explicitly linked observations. Do not infer links from a shared candidate key.

| Existing entity field | Stored definition |
|---|---|
| `TransactionOccurrence.id` | Required unique integer primary key. |
| `TransactionOccurrence.transaction_date` | Required date. |
| `TransactionOccurrence.amount_minor` | Required signed 64-bit integer EUR cents. |
| `TransactionOccurrence.currency` | Required currency, constrained to `EUR`. |
| `TransactionOccurrence.booking_status` | Nullable `pending` or `booked`; null only for an unresolved occurrence. |
| `TransactionOccurrence.reconciliation_state` | Required `confirmed`, `unresolved`, or `pending-only`. |
| `TransactionObservation.operation` | Nullable source operation text. |
| `TransactionObservation.details` | Nullable source details text. |
| `TransactionObservation.category` | Nullable bank-suggested category text. |
| `TransactionObservation.booking_status` | Required source status, `pending` or `booked`. |

An unlinked occurrence can be unresolved; it has no confirmed source description or category. Identical visible values do not identify an occurrence. Present observations separately and identify conflicting or absent values without inventing a representative fact.

## Transaction filters and projections

| Field | Validation and meaning |
|---|---|
| `date_from`, `date_to` | Optional ISO dates, inclusive; from cannot exceed to. |
| `booking_status` | Optional `pending`, `booked`, or `unknown`; unknown maps only to a null occurrence status. |
| `text` | Optional case-insensitive substring in the operation or details of any linked observation; literal characters, not SQL wildcard patterns. |
| `category` | Optional exact bank-suggested category, or explicit `no_recorded_category`; the latter means no linked observation has a non-null category, including no links. |
| `amount_min`, `amount_max` | Optional nonnegative decimal EUR strings, inclusive against absolute amounts; at most two fractional digits, exact integer cents from 0 through 2^63; minimum cannot exceed maximum. |
| `direction` | Optional `withdrawals` (amount < 0) or `deposits` (amount > 0); omitted/null means All, including zero. |
| `cursor` | Optional position in descending transaction date, then descending occurrence ID; must match the current filters. |
| `page_size` | Positive bounded integer, default 100, maximum 100. |

All active filters combine with AND. Text and category use separate existential checks against linked observations, and can match different observations. Return one projection per occurrence. Compute the result page and whether any history exists in one SQL statement or a repeatable-read transaction, so zero history and no filter matches are distinct even during an import. Clear filters resets the cursor. Stable ordering avoids merging identical-looking occurrences; pagination does not promise a frozen snapshot across concurrent imports.

The list projection contains occurrence ID as a decimal integer **string**, date, signed minor-unit amount as a decimal integer **string**, currency, booking status or `unknown`, reconciliation state, ongoing-expense boolean, and sorted distinct non-null linked `operations` and `details` arrays. Strings avoid browser precision loss for 64-bit values. Empty arrays explicitly indicate missing source text. Only non-unresolved pending debits are ongoing expenses. The detail projection contains these fields plus all linked observations' operation, details, source category and status; missing values are null, and an empty collection means no linked evidence. Financial values are never converted through binary floating point.

## UI import run (new PostgreSQL entity)

| Field | Meaning and constraints |
|---|---|
| `id` | Opaque generated UUID supplied by the UI or generated by the server; identifies the UI run, not a transaction. |
| `state` | `running`, `succeeded`, `no_files`, `failed`, or `unknown`. |
| `started_at`, `finished_at` | Timezone-aware timestamps; `finished_at` absent while running. |
| Result counts | Nullable non-negative `files_seen`, `files_processed`, `files_unchanged`, `rows_read`, `transactions_added`, `transactions_updated`, `observations_unchanged`, `unresolved_observations`; populated for successful or no-files outcomes. |
| `error_code` | Allowlisted error code, required for `failed` and null otherwise. |
| `error_message` | Sanitized message, required for `failed` and null otherwise; never input paths, credentials, account references or financial values. |

The selected folder path is validated input kept only for the lifetime of the task. Do not persist it, include it in a URL, or log it. Do not store workbook contents, observations, or financial values in run records. A successful zero-file discovery maps to `no_files`; a repeated import with files present remains `succeeded`, with unchanged counts. Only user-initiated UI runs appear in this table; CLI imports retain their existing contract.

## Run lifecycle and ownership

1. A local UI process obtains and retains a dedicated session-level PostgreSQL advisory lock on its own connection before accepting UI imports. If the lock is held by another UI process or the database is unavailable, starting an import is rejected explicitly. The UI can still open and display storage errors; it can retry acquisition after storage recovers. Do not reuse the existing ingestion advisory-lock key.
2. With the lock held, recover prior persisted `running` rows to `unknown` before accepting a new UI import. Only the lock holder may perform this recovery. The lock connection is owned for the UI process lifetime and never returned to the pool while locked. If it is lost, stop accepting work, cancel and await any owned import task safely, and do not claim its outcome.
3. Validate input, atomically insert `running`, and schedule one owned async task. In-process start serialization and the singleton lock prevent concurrent UI runs. If persistence fails, no task starts and the error is explicit.
4. The task calls the existing workbook discovery and public ingestion service with shared async infrastructure. Bind the ingestion write transaction to the same pinned connection holding the singleton lock, extending the public ingestion/session boundary as needed without changing the engine-based CLI contract. Do not silently reconnect that connection after lock loss: a task using a lost connection must not continue writing under a replacement session. This prevents a former lock holder from committing after another UI process acquires the lock. With storage available, the existing CLI's no-files result and import counts apply; the UI requires storage before discovery. Atomic transaction, account validation, duplicate handling, and the separate transaction-level PostgreSQL lock remain authoritative.
5. Once completion is confirmed, persist `succeeded` or `no_files` and counts, or `failed` and an allowlisted safe error only when failure and rollback are confirmed. A connection loss during commit or another uncertain commit outcome is `unknown`, not `failed`. Persist `unknown` when the service cannot establish whether the import committed. If terminal-state persistence fails, mark the in-process run indeterminate, expose an explicit unavailable/unknown outcome rather than success or perpetual running, and do not accept a new run until the stored state can be reconciled; recovery converts a leftover `running` row to `unknown`.
6. On refresh or reopening, the client queries the most recent UI run. While it is live, show the import screen and block navigation. On process restart, report recovered `unknown` explicitly; a user may inspect transactions and intentionally retry. Do not assume an interrupted import failed.

No automatic retry, cancellation control, progress percentage, or history browser is required. Polling observes state and is not the owner of the task.

### Workbook deadlines and cleanup

The existing thread-offloaded workbook functions have no deadline; cancellation of a thread await does not stop its underlying work. For UI imports, execute discovery, each workbook read/parse, and final snapshot verification in an owned local worker subprocess, one operation at a time. Await each operation with a 60-second deadline. Keep the existing CLI path unchanged. Extend the ingestion public boundary to use this worker for UI file operations; retain the existing parser, snapshot rules, and database transaction rather than duplicating ingestion logic.

The worker receives only the data required for file operations over local pipes, has no database connection or inherited credentials, and cannot write transaction data. Launch it with a sanitized environment and close unrelated file descriptors. Financial data and paths sent over pipes are not logged or persisted as temporary files. Transfer data in bounded chunks, retain the existing per-workbook safety limits, and do not impose a new aggregate limit on the number of eligible files. The parent owns all database work and the pinned lock connection.

On timeout, cancellation, lock loss, or shutdown, stop accepting results from the worker, terminate it, wait up to 5 seconds, then kill it and wait up to another 5 seconds. Do not start a replacement worker or a new UI import until the old worker is confirmed reaped. If it cannot be reaped, surface an explicit coordinator-unavailable error and keep new imports disabled; do not claim cleanup succeeded. A timeout is a sanitized failure only after confirming that no database transaction committed or that rollback completed; otherwise record or report `unknown`. A timeout during final verification must roll back the import transaction.

On orderly shutdown, allow the import task a 5-second grace period, then cancel and await it with the worker termination procedure above. Preserve `unknown` whenever the commit outcome cannot be confirmed. Database connections retain the existing 10-second connection and 60-second command timeouts.

Browser requests have a 75-second deadline. A timed-out import-start request may already have started work: do not automatically resubmit it; look up the requested run by ID and show status unavailable/unknown until its outcome can be established. Retain opaque request IDs in local storage across tab closure without storing the folder or financial data; if storage is unavailable, prevent starting and explain why. Look up the latest run alongside each requested run in one database snapshot so a later running import still blocks navigation. A timed-out status request likewise must not imply completion. Keep the start and in-application navigation blocked while a submitted run may still be active, explain the uncertainty, and allow retrying the status request. For an absent ID, an explicit recovery action uses the owned coordinator lock and start gate to insert a durable `unknown` record if absent; an existing record is never overwritten. Starts atomically refuse an already recorded ID, so a delayed request cannot run after this record is committed. Recovery cannot proceed while an import is active or ownership is unavailable; the user may inspect transactions and intentionally start a new request after recovery. Multiple tracked terminal outcomes remain individually visible until explicitly dismissed. Transaction read timeouts are retrieval failures, not empty results.

## Schema and migration

Create a reviewed Alembic revision for the import-run table, checks for supported states and non-negative counts, and an index for finding the most recent run. Do not create tables at runtime or change the ingestion occurrence/observation schema. Migration tests must upgrade both an empty database and the previous supported schema populated with representative transactions, checking retained data; test downgrade according to the project's migration conventions. Only PostgreSQL testcontainers provide database integration evidence.
